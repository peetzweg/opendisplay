# University Wi-Fi connection incident — 19 October 2026

## What happened

The 0.0.17 installer worked on home Wi-Fi. At university, with Tailscale running
and OpenDisplay open, native Screen Mirroring repeatedly failed before receiving
the phone's hello. The installed configuration still targeted `*.local` through
Bonjour/LAN. It had no saved VPN fallback.

Earlier Tailscale testing used an explicit VPN address on an earlier build.
Automatic setup subsequently saved a LAN hostname. That earlier success did not
validate a fresh automatic install on a restricted network. The 0.0.17 release
explicitly listed final-candidate Tailscale testing as outstanding; nevertheless,
our testing/release process did not make this required daily workflow a gate.

## Evidence and diagnosis

- Mac log: `iPhone receiver did not answer` during repeated native SETUP attempts.
- Direct control-port probes: local hostname timed out; the same phone answered
  with an OpenDisplay hello through its Tailscale address in about 0.23 seconds.
- Tailscale reported both devices online.
- `prepareTailscale` only ran for an already selected VPN target. The saved LAN
  target therefore did not become a VPN target just because Tailscale was on.
- After adding an optional verified fallback locally: two VPN playback sessions
  were confirmed, the latest reported 37–58 fps, and the user confirmed desktop
  updates and audible sound. One earlier receiver-closed/locked event was
  followed by successful playback; do not misreport this as zero total errors.

University client isolation or blocked local discovery is a plausible network
explanation, but the precise campus policy was not established. The supported
conclusion is route failure: LAN did not answer, VPN did. There is no evidence
that a recent video/UI change broke the underlying VPN transport.

Private logs, backups and device identifiers remain outside this document.
The installed hotfix has not been published in a new installer.

## Immediate fix and limits

Keep the saved LAN target and device identity. Try that existing path first,
with its existing three-second receiver deadline. If a configured VPN fallback
exists and the primary cannot handshake, prepare Tailscale and try the fallback.
Do not interrupt an already handshaken primary connection just to use VPN.
Reset the selected route to LAN for each new session. Preserve the optional
fallback in upgrades. The installed runtime, plist and configuration were backed
up before the patch; logs were not truncated.

26 targeted automated checks passed and the university playback check passed.
This does NOT prove a newly downloaded installer automatically discovers or
configures the correct VPN peer: the verified fallback was configured by the
developer during diagnosis. Home-return behavior is also still untested on this
candidate. These are explicit release blockers, not completed tests.

## Process failure

We confused separate scopes of evidence:

1. An explicit VPN-address test versus automatic setup and route selection.
2. An older source/build versus the exact installer being distributed.
3. Socket/protocol simulations versus real native-picker playback.
4. Passing home Wi-Fi checks versus support on restrictive Wi-Fi.

A high test count did not cover these missing combinations. Repeatedly fixing
symptoms without requiring the network transition matrix allowed this gap.

## Prevention

Follow [RELEASING.md](RELEASING.md) for every subsequent helper release.
`check-release.js` rejects dirty/unidentified builds, mismatched ZIP checksums or
commits, incomplete/failed/skipped TAP results, missing native checks, and missing
physical scenarios. Fresh-install network cases cannot count developer IP/plist
overrides as success. All scenarios must refer to the same frozen artifact.

CI and the standard verification command enable native, virtual, real-decode and
soak tests; verification also runs native CTest. CI artifacts are review builds,
not proof of physical compatibility. The release checker validates recorded
attestations; it cannot independently observe a phone or prevent an account owner
from manually bypassing the workflow. No claim that regressions are impossible.
